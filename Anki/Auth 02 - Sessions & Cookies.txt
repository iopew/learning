HTTP keeps no memory between requests. In a web app with cookie-based login sessions, what does the cookie hold, what does the server-side <code>sessions</code> table hold, and how do they combine to recognize a returning user?	The cookie holds only a random token, which the browser sends back on every request. The table row holds <code>token</code>, <code>user_id</code> and <code>expires_at</code>. The server looks up the token to find the user.
In web authentication, why can a server-side session be revoked instantly, while a JWT (JSON Web Token) can't be revoked without extra machinery?	A session is a row in the server's database: <code>DELETE</code> it and the token stops working. A JWT is carried by the client, so revoking it early needs a server-side blocklist.
A web app puts the user's <code>user_id</code> directly into the login cookie's value instead of a random token. What goes wrong, and what is the correct design?	The client controls the cookie, so editing <code>3</code> to <code>4</code> makes the app treat them as user 4 (an IDOR: insecure direct object reference). The value must be an opaque random token; <code>user_id</code> lives only in the server's <code>sessions</code> table.
In HTTP cookies, what do the <code>HttpOnly</code> and <code>Secure</code> attributes each do, and when should each be turned on for a login cookie?	<code>HttpOnly</code> stops JavaScript (<code>document.cookie</code>) reading the cookie, which blocks token theft via XSS (cross-site scripting): always on. <code>Secure</code> sends the cookie only over HTTPS: on in production with TLS, off for plain-HTTP local development.
A login cookie is set with <code>Path=/notes</code>, and logout lives at <code>/logout</code>. What breaks, and what should <code>Path</code> be? Also, what does setting <code>Domain=.example.com</code> change compared with leaving <code>Domain</code> empty?	The browser only sends the cookie to <code>/notes</code> paths, so the logout handler never receives the token. Use <code>Path=/</code>. An empty <code>Domain</code> means the current host only; <code>.example.com</code> also sends the cookie to its subdomains.
In Go's <code>net/http</code>, predict the exact header this writes, and explain what <code>MaxAge: -1</code> and <code>MaxAge: 0</code> each mean:<pre><code>w := httptest.NewRecorder()<br>http.SetCookie(w, &amp;http.Cookie{Name: "c", Value: "", Path: "/", MaxAge: -1})<br>fmt.Println(w.Header().Get("Set-Cookie"))</code></pre>	<code>c=; Path=/; Max-Age=0</code>. <code>MaxAge: -1</code> means "delete now", which Go writes as <code>Max-Age=0</code>. <code>MaxAge: 0</code> means no Max-Age attribute at all: the cookie lasts until the browser closes, unless <code>Expires</code> is set.
In Go's <code>net/http</code>, predict the output, then name the HTTP header that carries cookies from server to browser and the one that carries them from browser to server:<pre><code>r := httptest.NewRequest("GET", "/", nil)<br>r.Header.Set("Cookie", "session=abc; theme=dark")<br>c, _ := r.Cookie("session")<br>fmt.Println(c.Value)</code></pre>	<code>abc</code>. Server to browser: the <code>Set-Cookie</code> response header (name, value and attributes). Browser to server: the <code>Cookie</code> request header, listing every matching cookie as <code>name=value</code> pairs.
This Go login handler should set a session cookie and then redirect. Spot the bug and fix it:<pre><code>http.Redirect(w, r, "/notes", http.StatusSeeOther)<br>http.SetCookie(w, &amp;http.Cookie{Name: "session", Value: token, Path: "/"})</code></pre>	<code>http.Redirect</code> calls <code>WriteHeader</code>, which sends the headers, so the later <code>Set-Cookie</code> is never sent and the user bounces back to login. Fix: call <code>http.SetCookie</code> first, then <code>http.Redirect</code>.
In a SQLite <code>sessions</code> table, why is <code>token</code> declared <code>TEXT PRIMARY KEY</code> rather than <code>INTEGER</code>, and what is an index on <code>expires_at</code> for?	The token is a 64-character hex string, not a number; as the primary key it is unique and fast to look up. The <code>expires_at</code> index makes the periodic <code>DELETE ... WHERE expires_at &lt; datetime('now')</code> cheap.
In SQLite, <code>sessions.user_id</code> has <code>REFERENCES users(id) ON DELETE CASCADE</code>, yet deleting a user from a Go program (<code>database/sql</code> with the <code>modernc.org/sqlite</code> driver) leaves their sessions behind. Why, and how do you fix it?	SQLite ignores foreign keys unless they are switched on for each connection, and a one-time <code>PRAGMA foreign_keys = ON</code> only reaches one connection in the pool. Enable it in the DSN: <code>sql.Open("sqlite", "file:app.db?_pragma=foreign_keys(1)")</code>.
In SQLite, predict the result of this query and explain it:<pre><code>SELECT '2026-09-29T10:00:00Z' &gt; '2026-09-29 12:00:00';</code></pre>	<code>1</code> (true). TEXT values are compared character by character, and <code>'T'</code> sorts after <code>' '</code>, so the earlier 10:00 time looks later than 12:00.
A Go app stores session expiry in SQLite as shown and validates it with <code>WHERE token = ? AND expires_at &gt; datetime('now')</code>. Spot the bug and write the fix:<pre><code>exp := time.Now().Add(7 * 24 * time.Hour).Format(time.RFC3339)</code></pre>	RFC3339 (with its <code>T</code> separator and <code>+05:00</code> offset) doesn't match the text format of <code>datetime('now')</code>, so expired sessions still pass on their expiry day. Fix: <code>time.Now().UTC().Add(7 * 24 * time.Hour).Format("2006-01-02 15:04:05")</code>.
A Go server in a UTC+5 timezone stores <code>time.Now().Add(time.Hour).Format("2006-01-02 15:04:05")</code> as a session's expiry, and SQLite checks it against <code>datetime('now')</code>, which is UTC. How long does the session really last, and what's the fix?	About 6 hours: the local time is stored without a timezone, and SQLite reads it as UTC, 5 hours later. Fix: use <code>time.Now().UTC()</code>.
Write a Go function that returns a session token built from 32 random bytes, hex-encoded. How long is the resulting string?	<pre><code>func generateToken() (string, error) {<br>    b := make([]byte, 32)<br>    if _, err := rand.Read(b); err != nil { // crypto/rand<br>        return "", err<br>    }<br>    return hex.EncodeToString(b), nil<br>}</code></pre>64 characters: hex writes each byte as two characters from <code>0-9a-f</code>.
For a Go web app's session tokens, why use <code>crypto/rand</code> rather than <code>math/rand</code>, and why 32 random bytes rather than a random UUID?	<code>math/rand</code> is predictable, so tokens could be guessed. A UUID has only 122 random bits; 32 bytes give 256 bits (64 hex characters), the minimum for a session token.
This Go code runs after a password check succeeds. Spot the bugs:<pre><code>userID, _ := st.FindUserIDByEmail(email)<br>token, _ := generateToken()<br>st.CreateSession(token, userID, exp)</code></pre>	Every error is thrown away. A failed lookup makes <code>userID</code> <code>0</code>, so a session is created for a user who doesn't exist. A failed generation makes <code>token</code> <code>""</code>, so an empty-token session is stored. Check each <code>err</code> and return a 500.
In Go's <code>net/http</code>, predict the <code>Set-Cookie</code> header written for a value containing a semicolon (Go also logs a warning), and say why this would break a session:<pre><code>w := httptest.NewRecorder()<br>http.SetCookie(w, &amp;http.Cookie{Name: "a", Value: "x;y"})<br>fmt.Println(w.Header().Get("Set-Cookie"))</code></pre>	<code>a=xy</code>. Go silently drops invalid bytes like <code>;</code>, so the browser's value no longer matches the token in the database. Hex-encoded tokens (<code>0-9a-f</code> only) never hit this.
In Go's <code>net/http</code>, what does <code>r.Cookie("session")</code> return when the request has no such cookie? Spot the bug in this handler and fix it:<pre><code>c, err := r.Cookie("session")<br>if err != nil {<br>    http.Redirect(w, r, "/login", http.StatusSeeOther)<br>}<br>token := c.Value</code></pre>	It returns <code>(nil, http.ErrNoCookie)</code>, its only possible error. The <code>if</code> has no <code>return</code>, so execution reaches <code>c.Value</code> with <code>c == nil</code> and panics. Add <code>return</code> after the redirect.
A Go store has two session lookups. One selects <code>user_id, expires_at WHERE token = ?</code> and compares the expiry in Go; the other uses <code>WHERE token = ? AND expires_at &gt; datetime('now')</code>. How does each report an expired token, and what can only the first do?	The first finds the row and reports "expired" separately from "not found" (<code>sql.ErrNoRows</code>), so the caller can delete the stale row. The second returns <code>sql.ErrNoRows</code> for both, in one atomic query with no time parsing in Go.
Spot the security bug in this Go/SQL session lookup, and explain why relying on the cookie's <code>Expires</code> attribute is not a fix:<pre><code>db.QueryRow("SELECT user_id FROM sessions WHERE token = ?", token).Scan(&amp;uid)</code></pre>	There's no expiry check, so a token stays valid until someone deletes the row. <code>Expires</code> is only a request to the browser, which can ignore it; the database is the source of truth. Add <code>AND expires_at &gt; datetime('now')</code>.
In a Go web app with a SQLite <code>sessions</code> table, why must expired sessions be deleted, and when should the deletion run? Write it as an hourly background goroutine.	Otherwise expired rows pile up forever. Run it on startup and on a timer (or on every authenticated request, which is cheap with an <code>expires_at</code> index):<pre><code>go func() {<br>    ticker := time.NewTicker(time.Hour)<br>    defer ticker.Stop()<br>    for range ticker.C {<br>        st.DeleteExpiredSessions() // DELETE ... WHERE expires_at &lt; datetime('now')<br>    }<br>}()</code></pre>
Logout for cookie sessions should both delete the session row and tell the browser to delete the cookie. What goes wrong if you only do one of the two?	Only <code>DELETE</code>: the browser keeps sending a dead token, and every request does a failed lookup. Only clearing the cookie: the row stays in the database, so the token itself is still valid until it expires.
A Go logout handler clears the session cookie like this. Spot the bug and fix it:<pre><code>http.SetCookie(w, &amp;http.Cookie{Name: "session", Value: "", Path: "/", MaxAge: 0})</code></pre>	<code>MaxAge: 0</code> doesn't delete anything: it just omits <code>Max-Age</code>, so the browser keeps an empty cookie until it closes. Use <code>MaxAge: -1</code> (sent as <code>Max-Age=0</code>), optionally with <code>Expires: time.Unix(0, 0)</code>.
Compare a cookie, <code>localStorage</code> and <code>sessionStorage</code> for holding a login token: which is sent to the server automatically, which can JavaScript read, and which should hold the token?	Only the cookie is sent automatically, and only the cookie can be made unreadable to JavaScript (<code>HttpOnly</code>). <code>localStorage</code> and <code>sessionStorage</code> are readable by any script, so XSS can steal the token (<code>sessionStorage</code> is also lost when the tab closes). Use an <code>HttpOnly</code> cookie.
A page has two cookies: <code>session=abc</code> (<code>HttpOnly</code>) and <code>theme=dark</code> (not <code>HttpOnly</code>). What does <code>console.log(document.cookie)</code> print, and why does that matter for security?	<code>theme=dark</code>. <code>HttpOnly</code> cookies are hidden from JavaScript, so injected script can't read the session token; a token in <code>localStorage</code> could be read.
Compare the cookie attributes <code>SameSite=Lax</code> and <code>SameSite=Strict</code> on two events: an attacker's site auto-submitting a POST form to your app, and a user clicking a link to your app from an email.	<code>Lax</code>: the cookie is not sent on the cross-site POST (CSRF, cross-site request forgery, is blocked) but is sent on the link click, so the user arrives logged in. <code>Strict</code>: sent on neither, so the link click arrives looking logged out.
What does a browser require of a cookie with <code>SameSite=None</code>, and when is <code>None</code> appropriate?	It must also be <code>Secure</code> (HTTPS only), or the browser rejects it. <code>None</code> sends the cookie on every cross-site request, so use it only for iframes or cross-site APIs.
A login cookie already has <code>SameSite=Lax</code>. Why also put a hidden CSRF (cross-site request forgery) token in every POST form?	Defense in depth: two independent layers. The browser enforces <code>SameSite</code>, and the server checks the hidden token on every POST, so forged requests are blocked even if one layer fails.
In Go, a login cookie should last 7 days. Predict the output, and say what unit <code>http.Cookie.MaxAge</code> uses:<pre><code>fmt.Println(int(7*24*time.Hour.Seconds()), 7*24*3600)</code></pre>	<code>604800 604800</code>. <code>MaxAge</code> is in seconds, so both forms are correct. The alternative is an absolute time: <code>Expires: time.Now().Add(7 * 24 * time.Hour)</code>.
A Go web app has <code>POST /login</code>, <code>GET /notes</code> and <code>GET /logout</code>, backed by a <code>sessions</code> table. Using curl with <code>-c jar.txt</code> and <code>-b jar.txt</code>, how do you prove that login and logout work?	<code>-c</code> saves response cookies to the jar and <code>-b</code> sends them back, like a browser. Login should return <code>Set-Cookie: session=...</code>, <code>/notes</code> with the jar should return 200, logout should return <code>Set-Cookie: session=; Max-Age=0</code>, and <code>SELECT COUNT(*) FROM sessions</code> should show the row is gone.
